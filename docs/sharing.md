# 团队资料共享

我保留了 `team_open`，因为有些团队确实希望成员互相接续工作。但我不会把某个团队的选择当成所有团队的默认制度。公开版的本地演示、空配置和默认策略都保持关闭。

## 开启会发生什么

`framework/anc/policy.py` 在开关开启时，允许已核验、活跃的成员读取其他成员已进入 Loom 的资料，**包含私聊来源的记录和已有历史**。这是读取和披露策略，不是采集许可，也不会替你打开飞书历史或微信接入。

这里的“私聊”只表示消息来自私人会话，不保证资料在开启共享后仍只对发信人可见。开启前我会要求部署者向相关成员讲清这一点，确定哪些入口和资料会进入系统，并保存可核对的批准依据。对有敏感私聊、职务分级或外部客户资料的团队，不适合直接使用这个全局选项。

模型不能从聊天中的自称、昵称或一句“大家都同意了”修改策略。仍由获准管理入口核实身份、受众和当前配置；不活跃或未经核验的成员不因开关获得访问。

## 新成员接入也要单独确认

飞书私聊接入启用后，同一个已服务企业的账号第一次私信 bot，现有程序会自动登记为已核验团队成员。它不授予额外角色或具体授权，但如果同时开启 `team_open`，新登记成员也可能读到团队已有资料。管理员必须确认“同企业就是这个团队”是否适合自己的部署；不适合时先限制入口和登记范围，不能只靠昵称区分。

这个动作由真实私聊触发，不是后台遍历企业成员。我把它写出来，避免把“没有额外角色”误读成“开启共享后仍没有资料访问”。

## 如何查看、开启和关闭

命令中的 `<control>` 是你自己的测试或部署控制目录，`<批准依据>` 应替换为真实有效依据。先在副本里核对，不要照抄演示目录操作生产环境。

```sh
# 只看计划，不修改
python framework/tools/policy_open.py --control <control> --approval "<批准依据，至少12字符>"

# 管理员明确启用
python framework/tools/policy_open.py --control <control> --approval "<有效的启用批准依据>" --apply

# 关闭
python framework/tools/policy_open.py --control <control> --approval "<有效的关闭批准依据>" --off --apply
```

工具在任务或发送仍在处理时拒绝变更；不通过重启强行打断。变更会更新权限版本，旧任务必须重新核对权限。

关闭会恢复普通资料授权检查，不会收回此前已经看到、收到或导出的内容。备份也可能保留旧记录；删除、保留期限和访问撤销是不同操作，需要按实际制度处理。

本地演示会依次验证关闭时拒绝、明确开启后允许、再次关闭后拒绝，最后恢复关闭。全部对象和批准说明都是合成的。
